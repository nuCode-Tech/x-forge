# Python Auto-Loader Design

**Date:** 2026-03-11

## Problem

App developers using a Python plugin that wraps a Rust native library (via xforge) currently have to manually call `get_library_path()` or `load_native_library()` to download and load the binary. The goal is for the app developer to `import my_plugin` and have everything work transparently — the same experience Dart provides via `PrecompiledBuilder`.

## Chosen Approach: Generated Loader Module (Approach C)

`xforge generate-loader` is a CLI command the plugin author runs once during development. It produces a small `_xforge_loader.py` file that they commit into their package. That file auto-downloads, verifies, extracts, and loads the native library at import time. The app developer never sees or touches xforge.

This mirrors how Dart's `PrecompiledBuilder` is declared once by the plugin author and runs transparently during the build.

## Components

### 1. `xforge.loader` — new runtime module (`src/xforge/loader.py`)

Provides `load_or_raise(crate_dir, crate_rel_path, fallback_builder=None)`:

- Resolves the crate directory relative to the caller's `__file__` using `crate_rel_path`.
- Respects `XFORGE_NATIVE_LIB_PATH` env override (skip download, use that path directly).
- Calls `PrecompiledResolver.resolve()` to download, verify, and extract the library.
- Loads the extracted `.so`/`.dylib`/`.dll` via `ctypes.CDLL` and returns the handle.
- If resolution fails and `fallback_builder` is `None`: raises `RuntimeError` with a clear message.
- If `fallback_builder` is provided: calls `fallback_builder(crate_dir, reason)` which must return a `Path` to the library; then loads and returns that.
- Logs via `logging.getLogger("xforge.loader")` at INFO/DEBUG levels.

### 2. `xforge generate-loader` — new CLI command (added to `src/xforge/cli.py`)

```
xforge generate-loader [--out PATH]
```

- Auto-detects crate dir by searching for `xforge.yaml` in: `.`, `../native`, `../rust`, `../..`.
- `--out` specifies output path (default: `./_xforge_loader.py`).
- Validates `xforge.yaml` has a valid `precompiled_binaries` block before generating.
- Writes the generated file with a re-run comment header.

### 3. Generated `_xforge_loader.py`

```python
# AUTO-GENERATED by xforge generate-loader. Do not edit manually.
# Re-run: xforge generate-loader --out <this_file>
import ctypes
from xforge.loader import load_or_raise

LIBRARY: ctypes.CDLL = load_or_raise(
    crate_dir=__file__,
    crate_rel_path="../native",  # relative path from this file to the crate dir
    fallback_builder=None,       # replace with your own build function if needed
)
```

Plugin author's `__init__.py`:

```python
from . import _xforge_loader          # triggers download on first import
_lib = _xforge_loader.LIBRARY         # ctypes.CDLL, ready to use
```

### 4. Fallback pattern (mirrors Dart)

```python
# _xforge_loader.py after plugin author adds fallback
from xforge.loader import load_or_raise
from my_plugin._build import build_native  # plugin author's own Cargo wrapper

LIBRARY = load_or_raise(
    crate_dir=__file__,
    crate_rel_path="../native",
    fallback_builder=build_native,  # (crate_dir: Path, reason: str) -> Path
)
```

## Success Criteria

- `xforge generate-loader` produces a valid `_xforge_loader.py` given a crate with `xforge.yaml`.
- Importing the generated file downloads, verifies, extracts, and loads the library (or raises clearly if it can't).
- `LIBRARY` is a live `ctypes.CDLL` handle.
- `fallback_builder=None` raises `RuntimeError` on failure; a provided `fallback_builder` is called instead.
- `XFORGE_NATIVE_LIB_PATH` env override bypasses download.
- All new code has unit tests; existing tests still pass.
